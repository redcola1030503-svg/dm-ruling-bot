# T005: 全件クロールから漏れる特殊サブIDカード(DCR/spd等)への対応

Status: On Hold(対応案の検討段階でCodexレビューにより問題認識自体の誤りが判明。実装未着手。再開時はまず影響範囲の再調査から)

## Goal

T004(複数面カード名サジェスト漏れ修正)の本番`--force`全件再構築後、`card_index`に4,723件の「今回のクロールで見つからなかった」レコードが残存していることが判明した。サンプル確認した範囲では公式サイトから削除されたわけではなく実在するカードだった。全件クロールの取りこぼしの根本原因を特定し、対応案を検討する。

**重要(2026-09-03、Review 2で判明): 当初の問題認識自体が不正確だった。** `suggestCardNames()`は`updated_at`で絞り込んでおらず`card_index`の全行が検索対象のため、今回の`--force`で更新されなかった4,723件も**主要名は既に正常にサジェストされている**ことを本番APIで確認した(下記「再調査で判明した実態」参照)。「サジェストから漏れている」という前提で組み立てた対応案(案A/A')は、実際の課題規模に対して過大である可能性が高い。着手を保留し、次回再開時はまず実際の影響範囲(裏面名補完漏れが実害となるケースがどれだけあるか)を先に調べ直す。

## 調査結果(2026-09-03、Renderのシェル・DB・公式サイトを直接確認して判明)

- `card_index`のうち4,723件(全16,373件中)は、今回の`--force`実行(`updated_at`が新しくなっていない)で見つからなかった
- サンプル抽出したプレフィックス別件数: `dm26ex3` 220件、`dm26ss1` 191件、`dm24ex3` 182件、`dmex08` 128件 など多数のセットに分散
- **サンプル2件**(`dm26ex3-DCR006`「斬隠蒼頭龍バイケン」、`promoy23-spd1111`「ア:グンテ」)の詳細ページに直接アクセスし、実在することを確認した。**4,723件全体を分類・確認したわけではない**(この点は当初の報告で「全て実在」と断定していたが、根拠不足だったため訂正する)
- 確認した2件は、同一`dm26ex3`セット内の通常3桁連番ID(`dm26ex3-005`等、今回のクロールで正しく取得できている)とは異なり、特殊サブID(`dm26ex3-DCR004`のような再録カード枠、`promoy23-spd1111`のようなスタートデッキ付属カード枠)を持っていた
- 「斬隠蒼頭龍バイケン」というカード名で公式サイトのキーワード検索(`card_name`)を行うと、同名の別カード(`dm29-s02`)のみが1件返り、`dm26ex3-DCR006`はヒットしない。公式サイトの検索エンジン(名前検索・全件一覧検索とも)が、これら特殊サブIDのカードを検索結果に含めない仕様(または不具合)である可能性が高い
- 個別の詳細ページ(`/card/detail/?id=xxx`)には問題なくアクセスできる(確認した2件の範囲)

## 影響範囲(当初の認識と、Review 2後の訂正)

**当初の認識(誤り)**: 「該当4,723件がサジェスト候補に出てこない」という前提で影響範囲を組み立てていた。

**再調査で判明した実態(2026-09-03)**: 本番`GET /api/cards/suggest`に「斬隠蒼頭龍バイケン」で問い合わせたところ、`dm26ex3-DCR006`(未更新側)と`dm29-s02`(通常側)の**両方が返ってきた**。`suggestCardNames()`([cardIndexRepository.ts](../../src/cards/cardIndexRepository.ts))は`updated_at`を条件に含まず`card_index`の全行が検索対象のため、今回の`--force`で更新されなかった行でも、既存の主要名(name)は問題なくサジェストされる。つまり「サジェストに出ない」という問題は、確認した範囲では発生していない。

**未確認のまま残る、規模が縮小した可能性のある課題**:
1. これら4,723件がもし複数面カード(サイキック/ドラグハート/ツインパクト)だった場合、T004以前のスキーマ(`card_index_alt_name`未実装時)で登録されたレコードのままなら、**裏面名(alternateNames)のみ**が補完されていない可能性がある。実際に4,723件中どれだけが複数面カードかは未調査
2. 裁定生成側(`cardNameMatcher.ts`の`findCardCandidates`)は`searchOfficialCards`(公式サイトのキーワード検索API)に直接依存しており、`card_index`(ローカルDB)は一切参照していない([cardNameMatcher.ts:83](../../src/cards/cardNameMatcher.ts))。同名カードが複数存在する場合の解決は、Review 2で指摘の通り案A'を実装しても未解決の設計課題が残る(下記Review History参照)

**次回再開時に最初にやるべきこと**: 4,723件からサンプリングして、実際に複数面カード(裏面名補完漏れが実害になるケース)がどれだけ含まれるかを確認し、対応要否・優先度を判断する。

## 未解決の疑問(要調査)

- なぜ空keyword全件検索・キーワード名検索の両方からこれらのカードが漏れるのか、公式サイト側の正確な仕様は未特定
- 一度も`card_index`に登録されたことがない、完全に新規の特殊サブIDカードをどう発見するか。さらに、`cardIndexBuildJob.ts`の`checkForCardListUpdateAndMaybeReindex`が使う`fetchTotalCardCount()`([cardSearch.ts:38](../../src/cards/cardSearch.ts))も同じ検索エンジンの`total_count`表示に依存しているため、**特殊サブIDカードだけが新規追加された場合、再構築のトリガー自体が働かない可能性がある**(Codexレビュー指摘)
- 4,723件のうち、実際に「404/410で確認済み廃止」「一時的なエラーで取得失敗」「実在するが取得ロジックの問題」がそれぞれ何件あるかは未分類

## 対応案

### 案A: 既存`card_index`との差分検出による個別補完(部分的対応、既存DB救済に限定)

`collectAllCardHits()`で収集したIDの集合と、既存`card_index`テーブルの全ID一覧を比較し、「過去に存在したが今回のクロールで見つからなかったID」を特定して、個別に`getOfficialCard`で再取得を試みる。

**スコープの限定(Codexレビュー指摘を反映)**: 案Aは「既存`card_index`に一度でも登録されたことがあるカードの救済」にのみ有効。一度も登録されたことがない完全新規の特殊サブIDカードは検出できない。そのため案Aは必須対応の一部とし、**発見経路の恒久対策として案B or 案Cのいずれかも必須範囲に含める**(Codexレビュー指摘)。

実装イメージ(改訂版):
```typescript
// cardIndexRepository.tsに追加
export function getAllCardIndexEntries(): { id: string; url: string; updated_at: number }[] {
  return db.prepare("SELECT id, url, updated_at FROM card_index").all() as
    { id: string; url: string; updated_at: number }[];
}

// 確認済み404/410のみを廃止候補として記録する(一時的なエラーと区別する)。
// 例: card_index_meta等に候補を積み、別途人手 or 複数回の再確認を経てから削除する
// (取得失敗即削除はしない)。
```

**取得失敗の扱い(Codexレビュー指摘を反映)**: `getOfficialCard()`は404、一時的な5xx・タイムアウト、HTML構造変更によるパース失敗が同じ失敗経路(`null`または例外)に流れる([cardSearch.ts](../../src/cards/cardSearch.ts))。取得失敗を一律「廃止」として削除するのは、有効なカードを誤って消す危険がある。

- 削除候補にしてよいのは、HTTPステータスが**確認済み404/410**の場合のみ
- 一時的なエラー(5xx・タイムアウト・パース失敗)は別集計とし、削除しない(次回再試行)
- 実際に削除する場合は、`card_index`と`card_index_alt_name`を同一トランザクションで処理する(片方だけ削除されると別名だけサジェストに残る不整合が起きる)

**再取得頻度の制御(Codexレビュー指摘を反映)**: 特殊サブIDのカードは構造的に毎回`collectedIds`に含まれない。単純に「収集漏れ全件を`force:true`で再取得」する設計では、通常の差分更新(30日stale判定)を実行するたびに、この4,723件相当が毎回強制再取得され、約40分の追加処理が発生してしまう。以下のいずれか(複数可)で頻度を制御する必要がある。

- 個別のTTL(例: 前回の個別再取得から30日以内ならスキップする、`card_index`のカラムを流用または別テーブルで管理)
- CLIの明示オプション化(`--recover-missing`のような別フラグを新設し、通常の`--force`/差分更新とは独立して手動実行する)
- チェックポイント再開(4,723件の処理途中で中断・失敗しても、次回は未処理分から再開できるようにする)
- 進捗・結果集計(recovered/goneMissing/error等を分けて出力する)

### 案A': 裁定生成側(`cardNameMatcher.ts`)の同名カード解決の補強(案Aとは別スコープ、必須)

`findCardCandidates()`が`searchOfficialCards()`(公式検索)の結果だけでなく、ローカルの`card_index`/`card_index_alt_name`から前方一致・完全一致する候補も取得し、公式検索結果と統合・重複排除してスコアリング対象に含める。

- `card_index`にはid/name/urlのみのため、候補が見つかった場合は`getOfficialCard({id, url})`で詳細(cardType/civilization等)を個別取得する必要がある
- 同名だが内容(cardText等)が異なる再録カードが複数候補として並んだ場合の一意化・あいまい判定への統合方法を設計する必要がある
- 同名・異テキスト再録のケースを想定したテストを追加する

### 案B: 商品(セット)ページ経由でのカード一覧収集

公式サイトの商品情報ページ(例: 各拡張パックの収録カード一覧)から、セットごとのカードID一覧を収集し、空keyword全件検索を補完する。

- 利点: 新規の特殊サブIDカードも含めて網羅的に収集できる可能性がある。案Aでは検出できない「発見経路」の問題を解決しうる
- 欠点: 商品ページのHTML構造調査から必要で実装コストが高い。全商品ページを回る新たなクロールが必要になり、既存のクロール方式と別立てのロジックになる

### 案C: 検索クエリパラメータを変えた補完クエリ

`cardtype`や`products`(商品名)等のフィルタパラメータを使った検索を試し、特殊サブIDカードがヒットする条件を探索する。

- 利点: 既存の検索の仕組みを流用できる。案Bより実装コストが低い可能性がある
- 欠点: 現時点でどのパラメータが有効か未検証。今回の調査では`cardtype`フィルタ自体は機能することを確認済みだが、DCR/spd枠がどのcardtype値に分類されるか等は未調査。試行錯誤が必要
