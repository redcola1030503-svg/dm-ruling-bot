# T011: Batch API経由の裁定ジョブが、デプロイ(プロセス再起動)中に永久に`running`のまま残る

Status: **Closed(2026-09-04)**。本タスクが提案していた「batch_id永続化+起動時再照合」という個別対応は、T012の検討過程で「通常API経路でも同種のプロセス再起動問題が起こりうる」ことが判明したため不要になった。T012(A)の汎用的な孤立ジョブ回収(`src/ruling/orphanedJobSweep.ts`、起動時+5分間隔の定期走査+`finalizeRulingJob`による返金確定)を実装・ローカルdevサーバーで実機確認済み。**下記「対応方針」1〜3は実装していない(廃案のまま)**。本番デプロイ後、孤立ジョブXも自動回収される見込み(未デプロイ)。詳細は`.ai/tasks/T012-remove-batch-api.md`参照

## Goal

ユーザーから「裁定生成がかなり長い間止まっている」との報告を受け調査したところ、本番DBに`status='running'`のまま完了しないジョブが2件見つかった。原因を特定し、対応方針を固める。

## 調査結果(2026-09-04、コード確認・本番DB確認済み)

### 発見した事実

本番DB(`/app/data/cache.db`)の`ruling_job`テーブルを`status IN ('pending','running')`で確認したところ、2件がヒットした。

1. ジョブA: `status='running'`、作成から約15.5分経過(調査時点)
2. ジョブB: `status='running'`、作成から約2.4日(約57時間)経過(調査時点)

サーバー自体は健全(`GET /health`が`{"status":"ok"}`を即座に返す)。特定のジョブだけが完了しない状態。

### 原因(コード確認済み)

`src/llm/client.ts`の`completeJsonViaBatch`(Anthropic Message Batches API利用、入出力とも50%割引)が原因と考えられる。

```typescript
let current = batch;
while (current.processing_status !== "ended") {
  await sleep(BATCH_POLL_INTERVAL_MS); // 10秒間隔
  current = await anthropic.messages.batches.retrieve(batch.id);
}
```

コード内コメントに「通常『1時間以内』で完了するが保証はなく最大24時間かかりうる」と明記されている通り、Batch APIの完了には数分〜最大24時間の幅がある。この`while`ループは**プロセスのメモリ上でだけ**回り続ける設計で、`batch.id`はどこにも永続化されない。

- ジョブA(15.5分)は、Batch APIの通常範囲内(1時間以内)にまだ収まっており、**サーバープロセスが再起動していなければ、待てば完了する可能性が高い**。直近のデプロイ(2026-09-03 19:34 JST、T008反映、コミット`38275ea`)より後に作成されたジョブであり、その後デプロイは発生していない(Renderのデプロイ履歴で確認)。
- ジョブB(2.4日)は、Anthropicの規定上の最大値(24時間)を明確に超えている。作成時刻を逆算すると**直近のデプロイより前**に作成されたジョブだった。**Renderがこのサービスを再デプロイ(プロセス再起動)すると、ポーリング中の`while`ループごとプロセスが終了し、そのジョブは二度と完了しない**。DBの`ruling_job.status`は`running`のまま更新されず、`markDone`/`markFailed`のどちらも呼ばれないため永久に残る。

### 影響

- ユーザーは`GET /api/ruling/jobs/:jobId`をポーリングし続けても`status: "running"`のままで、いつまで待てばよいか分からない(モバイル側は無期限に「裁定を生成しています…」を表示し続ける)。
- プッシュ通知も送られない(`markDone`が呼ばれる`.then`内でのみ送信されるため)。
- 無料枠は既に消費済みのまま返ってこない(T010の対応が入れば、このケースも「回答を得られなかった」場合として返金対象に含めるべきだが、`markDone`/`markFailed`のいずれも呼ばれないケースはT010の設計(ジョブ確定時の返金判定)だけではカバーできない)。
- Renderは通常、新しいデプロイの前に既存インスタンスへ猶予期間([graceful shutdown](https://render.com))を与えるが、Batch APIの10秒間隔ポーリングループはこの猶予期間内に完了しない場合が普通にありうるため、通常のデプロイ運用(T003〜T010で繰り返し行っているコード修正のたびのデプロイ)のたびに発生しうる。

## 対応方針(ドラフト、詳細はCodexレビューで詰める想定)

1. **バッチIDの永続化**: `ruling_job`テーブルに`batch_id`列を追加し、Batch API呼び出し開始時点で保存する。プロセス再起動後もどのジョブがどのバッチに対応するか復元できるようにする。
2. **起動時の再照合(reconciliation)**: サーバー起動時、`status='running'`かつ`batch_id`が設定されているジョブを探し、Anthropic APIへ`batches.retrieve(batch_id)`で現在の状態を問い合わせる。`processing_status === "ended"`ならその場で結果を取得して`markDone`、まだ`in_progress`ならポーリングを再開する(またはバックグラウンドジョブとして再登録する)処理を追加する。
3. **アプリケーション側のタイムアウト**: Anthropic側の最大24時間という規定を踏まえ、`completeJsonViaBatch`の`while`ループ自体にも上限(例: 2〜3時間)を設け、超過した場合は`llm_error`相当として扱いユーザーへエラー応答を返す設計にする(現状は無期限に待ち続ける)。
4. **T010(裁定失敗時の返金)との関係**: このケースは`produceRuling`の`ProduceRulingOutcome`のいずれにも到達せず、`markDone`/`markFailed`が一切呼ばれないまま終わる特殊なケースのため、T010の「ジョブ確定処理での返金判定」だけではカバーできない。上記2(起動時の再照合)で最終的に`markDone`/`markFailed`のどちらかに到達させることができれば、T010の仕組みにそのまま乗せられる。設計順序として、T011(このタスク)を先に対応してから、T010が全ての失敗経路を正しくカバーできているか再確認するのが望ましい。
5. **運用上の代替策(コード変更なし)**: 今回発見したジョブB(2.4日放置)のような既存の孤立ジョブは、本番DBで手動的に`status='failed'`へ更新する応急処置が可能だが、根本対応(上記1〜3)を優先する。

## 未確定・要検討事項

- Batch APIそのものをやめて常に通常APIを使う(`RULING_USE_BATCH_API=false`)という選択肢も、コスト増(通常APIは50%引きの恩恵が無い)とのトレードオフとして検討の余地がある。ただしこれは既存のPricing検討([[project-dm-ruling-bot]]参照)と関係するテーマであり、本タスクのスコープ外とする。
- 起動時の再照合(上記2)は、Render起動直後の短い時間内に外部API(Anthropic)へ問い合わせる処理が入るため、起動シーケンス・ヘルスチェックへの影響を確認する必要がある。
